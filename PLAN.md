# Motion Lab — Plan

## What this is

Motion Lab is a reusable template for iterating on motion for components imported from any Figma file. It replaces an older claude.ai artifact hub.

- **Template repo (a17-motion-lab):** all lab features are built here. It stays client-agnostic.
- **Project repos (e.g. the pilot project repo):** made from the template. They hold client content only: components, versions, pages, presets, assets and baselines. They pull template updates and never build features.

## The job (decided 2026-11-05)

After a critical review of the tool, its job is three things, and every feature is judged against them:

1. **Ideate** on motion across a system of pages and components.
2. **Review** in a real browser, and share directly with clients.
3. **Hand off** to a developer without ambiguity (tokens, spec, export).

It is an animation studio for our own projects, and what makes it worth having is that the motion made in it **leaves the studio**: as a spec and code a developer builds from, or (later, the Storybook adapter) directly into the codebase. It does not try to out-feature Figma, Framer, Rive or After Effects at authoring. Tweaks stay as versions made through Claude; sliders and token tuning are a nice-to-have for later (tune a token and save it into the system). The Motion runtime and the global scale stay built but are de-emphasised: easing and GSAP are where the work is, and no new work goes into either.

**Staying focused (a drift check, not a freeze).** Tweaks and fixes go on as needed. Before building anything bigger, ask: (1) which of the three jobs does it serve, and does something real (a designer's use, a client review, a developer's build) need it now? (2) Does it make the tool easier or harder to pick up? (3) Does it help motion leave the studio, or only make authoring richer? A feature that serves none of the three is parked under Optional, not built. Revisit the list when the designer trial reports back, which should answer: is a Figma frame to an approved version faster than today, where did the designer want to drag instead of ask, and did a developer trust the spec.

It plays in the lab under both runtimes with state buttons, Toggle, Interrupt and a click on `data-motion-set`, and exports as CSS (`[data-state]` rules), GSAP and Motion. Findings: (1) **Motion's duration-based springs ignore inherited velocity** (source: "Time-defined springs ignore inherited velocity"; measured), so velocity carry-over, the point of supporting interruptions, needs **physics springs** (stiffness, damping, mass), which means a decision: add physics springs next to duration and bounce, derive them from duration and bounce with Motion's own formula (duplicating its logic), or accept that both runtimes just retarget; (2) CSS retargets from the current computed value, no speed carried (measured −130px/s before the reversal, +27 after); both runtimes retarget without a position jump; (3) Motion's `duration: 0` instant sets are unreliable on first use (the element stayed put); `duration: 0.001` and waiting works; (4) a transition is keyed by its target state because CSS, GSAP and Motion take timing on arrival; (5) `model` is still required on a version, so an interaction version carries a placeholder: make it optional; (6) exits are shorter than entrances, which the pairing rules caught (an expressive exit at 300ms warns), so exits use productive easings. ## Decisions

- No nested components on pages.
- No Claude GitHub Action for now; designers use Claude Code directly.
- Previews will be hosted on Twill (folder upload, password protected).
- `reference/old-motion-lab.html` (gitignored) is the old lab, for porting features only. Never copy client content from it.
- The motion-only rule: versions change motion, never structure.
- Motion tokens flow Motion Lab → Figma. `tokens/motion.json` is the source of truth for motion; Figma holds a read-only mirror in its own "Motion" variable collection. Visual variables still flow Figma → Motion Lab (import), so the two directions never share a collection.
- Motion changes are new versions, not tweaks. The component view has no controls (no duration or easing fields, no copy values), so a designer forks a version and edits it. Tokens come from the system: to use a value it doesn't have, an author adds a token (see token governance, on hold).
- Easing is the only family of motion curves: easings carry no spring form (removed 2026-11-01). Bounce tokens came back on 2026-11-01 as the one spring setting, shown under Motion only. A spring is a property of a version (its own `bounce`, a plain number), played only by Motion.
- The global scale is a project-wide decision, not a tweak: it is applied rarely, on request, after a preview, and it changes token names, so it is a setting (Settings panel), not part of the everyday views, and Figma is updated by renaming variables in place.
- **Runtime libraries.** The lab does not recreate library logic: it plays with a real runtime and never fakes what the library lacks. Decided and built: the switch (in Settings) is **CSS / Motion** (CSS is the default; Motion plays a spring version as a real spring, from the version's own `bounce`). **GSAP is an export format, not a preview runtime** (clients mostly use GSAP, but in the preview it would play the same cubic-bezier as CSS): the Generated CSS panel and `npm run spec -- <component> [version] --format gsap` write GSAP code (seconds, `CustomEase` for the easing, `stagger`, layers as timeline positions), easing only. A unit test loads GSAP, runs the generated code and checks its timeline against the CSS timing. Velocity carry-over from interrupted animations is only possible under Motion and is deferred. Steps: (1) done: remove spring faking, one CSS playback path; (2) done: Motion adapter and the CSS / Motion header switch; (3) done: export formats. The Generated CSS panel has a CSS / GSAP / Motion picker and `npm run spec -- … --format gsap|motion|all [--bounce N]` writes `motion.gsap.js` / `motion.motion.js` beside `motion.css` (see CLAUDE.md).
- A version can move more than the root: `layers`, keyed by the `data-motion` name of an inner element, each with its own duration, easing and delay (the card rises while its text rises and fades in). The component view's Tokens used panel is grouped by layer and says where each token sits in the motion.
- Pairing rules are warnings, never errors: productive easings with 100–300ms, expressive with 400–1200ms.
- Token status is `system` (approved) or `experimental`. New tokens start experimental; a renamed or merged token keeps the highest status of the tokens folded into it.
- Keyframes reference tokens (`translateY({distance.20})`, `-{distance.20}` for negatives). Spring `properties[]` `from`/`to` do not yet.
- The primitives can be regenerated from a scale (`npm run tokens:scale`). Names are values, so a new scale renames tokens and the references to them.
- Authors are the core users. Reviewers and tweakers get the hosted Lab. Getting started must still need as little setup as possible: a GitHub account, a machine setup and org repo admin per designer is a real cost for authors, so reducing it (or removing it, see step 8) is a product goal, not a nice-to-have.
- Authoring and iterating on motion happens in Claude. Figma's motion tools don't yet give designers what they need and are lossy when translated to our model, so Figma stays the source of visuals and a synced mirror of motion tokens, not the place motion is authored.
- What the Lab exports should be as close as possible to what a developer actually ships. Judge every export change by how little a developer has to reinterpret.
- Effort to start is a standing product concern. Every new feature should be weighed by whether it makes it easier or harder for a designer to pick the tool up and start working.
- The developer hand-off is stack-neutral CSS first. Library adapters (GSAP, Motion) are added only when a client's stack needs one.
- A version with no `trigger` is "not specified", never defaulted. The spec and CSS say so and tell the developer to ask. Imports never set a trigger.
- **Pages are components assembled, never whole-page copies.** A page version is a saved combination of component versions plus the stagger (see Next steps), so one component is explored once however many pages use it, and what a developer receives is still the approved component.
- **Source adapters, not modes.** Figma and (later) Storybook or a live URL are ways of producing a component; the lab, versions, pages and exports do not change with the source. A component records its source in `meta.json`.

- **Priority order, to revisit after the designer trial:** (1) hosted, shareable review links for clients (step 4 of the earlier list, Twill); (2) the Storybook adapter (steps 3–6 of Refinement), so motion is judged on the real component, not a Figma replica; (3) the presets spike (propose presets from commonalities in authored motion, with a UI to adopt them into `tokens/presets.json`); (4) controls that tune tokens and save them into the system. The Motion runtime and the global scale get no new work.

## Next steps

Motion Lab has two workflows, decided 2026-11-05. **Ideation** is early in a project: Figma is the source, there is no code yet, and a designer explores motion on a page and its components. **Refinement** is later, once the core system is built: the build is the source, components come from it (Storybook or a live URL), and designers refine motion against what ships. One model serves both: a component is markup, CSS and versions, a page is a list of components, and only where the markup comes from (and what v1 is) differs. Build ideation first, then refinement.

**Ideation (now)**

1. **Page from Figma.** A Figma page frame becomes components plus a page: Claude reads the frame, imports one component per section (repeated instances are one component), and writes `pages/<id>/page.json` listing them in order, with a first page version that plays every component's default version. Mostly workflow plus a small page-writing script; the Figma component import is unchanged.
2. **Page versions.** A page version is a named combination saved with its page (`pages/<id>/versions/<version>.json`): which component version plays in each slot (`motionMap`) and the page stagger. It replaces today's motion-map "preset", which has no page and doesn't save the stagger. The Page view lists a page's versions, switches between them and compares two side by side; the panel is renamed "Page versions" so it never clashes with the entrance presets. Page versions point at component versions (nothing is copied), and approval stays at the component level.

Status (2026-11-05): steps 1 and 2 are built and committed in the template (`scripts/figma-import/page.ts`, `lab/lib/page-versions.ts`, the Page view). First real run on a Jane Street page frame (1440×5136, seven sections plus menu, header and footer): six new components imported, each within the 5% visual check, the page written, and a second page version compared side by side. What the run showed: (a) one Figma component can appear in several shapes, here a "section header" three ways, so a section is a lab component per **shape**, named for what differs; (b) the frame's own variable modes make some variables read differently per frame (`space/7`, `space/12`, `space/11`), and the generated code's fallbacks can disagree with the rendered frame (80px against 160px), so the screenshot is the reference and only default-mode values are imported; (c) a section can be a wrapper around one child (the "uniform" grid is one prompts card), named after the child; (d) page chrome (menu, header, footer) is left for its own pass; (e) the Figma MCP sometimes answers `get_design_context` with a Code Connect question instead of the design, and a retry returns the design. Done since: the Page view is a fixed-height window you scroll, and a version with an in-view trigger waits until its section scrolls in (`lab/lib/scroll-trigger.ts`). Still to do for ideation: page transitions, and a menu-open/close interaction version.

Sample content (2026-11-05): the template's `card`, `side-panel` and `home` are samples its tests run on; a project repo deletes them and the tests that need them skip themselves (`tests/samples.ts`, a guard test, the lab defaults to the first component and page). Done in the template; the pilot is the first project to drop them.

**Refinement (later)**

3. **Codebase adapter.** Import a component from the build into the same component format: Storybook first (its `index.json` is the component list; stories give isolated rendering and states, the Jane Street one is behind HTTP auth, so credentials come from environment variables and are never committed), then a live URL. The agent extracts, a script writes, like the Figma import. Findings so far: that Storybook is React with CSS Modules (hashed class names) and Radix primitives (`data-state`, `data-slot`); a component's states often need an interaction first (a dialog only exists once opened); the story already has its own transitions that would fight a lab version.
4. **Layer mapping that survives re-import**, so a component started in Figma can switch to the build and keep its versions (selector to `data-motion` name, re-applied on every import).
5. **Existing motion as v1.** Read the build's transitions and keyframes into a v1 mapped to the nearest tokens, so designers refine what ships.
6. **Export back to the real selectors** (a patch a developer applies), instead of generated class names.
