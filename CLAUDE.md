## Architecture

**Shell**: Vite + vanilla TypeScript. No UI framework. **Look**: the Vitrine UI kit (its own **text styles** as `--type-*` font shorthands at the top of `lab/styles.css`, named for the kit's styles: `--type-heading-4`, `--type-heading-6`, `--type-ui-1`, `--type-ui-2` (+ `-strong`), `--type-caption`, `--type-label`, `--type-display`; use them with `font: var(--type-…)`, never a loose size or weight; the lab uses Suisse Int'l and Suisse Int'l Mono when they are installed on the computer (licensed, never committed; `/fonts` is gitignored), else Inter and IBM Plex Mono stand in; Inter, IBM Plex Mono, near-black and white; the kit's own gray scale, `--gray-50` to `--gray-950`, and its blues are the lab's palette, and every `--color-*` points at them: every card, panel and example frame is the kit's **background/secondary** (`--color-card`: `gray-50` `#f5f5f5`, `gray-900` in dark) (a card with a background has **no border**; `--color-border`, the kit's **border/default** at 12%, is only for an element with no fill of its own, such as a frame or dialog; hairlines such as rules, table lines and dividers use **border/subtle**, `--color-subtle`, 8%), never `--color-surface` or a loose gray; the darker `--color-image-bg` stays only behind a component preview inside a card), set in `lab/styles.css` under the lab's own `--color-*`, `--radius` and `--lab-font-*` variables, never a client's variable names; previewed content keeps a neutral font (`--lab-font-content`), never the lab's.
**Motion runtime**: the lab plays with a runtime chosen in **Settings** (the gear), **CSS / Motion** (CSS by default), and **never mixes them: CSS plays easing curves for every motion, Motion plays springs for every motion**, the root and every layer. **CSS** is the Web Animations API (`element.animate(keyframes, options)`). **Motion** is motion.dev's `animate`, a real library with springs. The lab simulates nothing a runtime lacks.
**Tokens**: W3C DTCG JSON (`tokens/motion.json`) → CSS custom properties + raw values.
**Components**: HTML/CSS prototypes with a `motion.ts` file that re-exports named motion versions, one file per version in `versions/`.
**Library**: `/?view=library` is **home** (opening the lab with no `view` shows it) and the way into every component: it lists each registered component as a scaled live preview (plays on hover). It builds from the component registry, so new components appear automatically; filters use `?status=…&archived=1&q=…` (a component's status). The toolbar above the cards has the search and the status dropdown together on the left, and the count and Show archived on the right, at 16px. Logic is in `lab/lib/library.ts`. **An empty project** (no components, or no pages) shows a short "ask Claude" screen in the Components, component and Page views instead of a blank one (`lab/lib/empty-state.ts`): a title, what to ask, ready-made requests with a Copy button, and a tip, in plain words (a unit test keeps git and code words out). **Navigation**: the top nav is **Components, Pages, Presets and Tokens** (the Components item is the Library view: its URL is still `?view=library`, its label, the breadcrumb's first link and the tab title say Components). **The four top-level views share one page header** (`heroEl` in `lab/main.ts`, `.lab-hero`): the view's name large on the page colour in a fixed zone so it sits in the same place on every view (160px high; a description goes under the title and makes the header taller), a rule under it, with that view's own controls below it in the **action bar** (`.lab-actionbar`: full width, 72px high, the page colour, sitting under the header's rule with none of its own; the Tokens tabs, the Components and Pages search and filters, the Presets Replay all (its description sits in the header under the title)), the pattern for any row of controls under a title; the component and page views keep their top bar instead. **Pages is a library of pages**, the way Components is of components (`?view=pages&q=…`, `renderPagesView`): each page is a card with its sections laid out at the page's own width and scaled to the card, plays its sections on hover, and says its title, sections and saved versions; a card opens the page view (`?view=page&page=<id>`), whose top bar is a `Pages / <page>` breadcrumb back to the library, and Pages stays the lit nav item while a page is open (a project with no pages shows the "ask Claude" screen); the items are real links and a plain click switches the view in place (history.pushState, no page load; `navigate` and the document click handler in `lab/main.ts`, the current one is `aria-current="page"`, and `route()` lets go of the old view's observers and animations first); there is no Component item, a component opens from its Library card (`?view=component&component=<name>`), and while one is open the Library stays the lit item. The logo goes to the Library. **The top bar** (`viewBarHtml` in `lab/main.ts`) is one full-width row above the example and the rail on the component and page views, so the two line up under it: where you are on the left (the breadcrumb on the component view and the page view) and the playback controls on the right, **Speed, a "Playing with Motion (springs)" chip that opens Settings when Motion is on, and Replay** (Replay All on the page view). Its icons (the Settings gear, the dialog's close) are SVG line icons in `lab/lib/icons.ts`, in the button's colour. **The project's name** (`project.json` at the repo root, `{ "name": "…" }`, the project's own: the template ships none) shows before the product in the header ("Jane Street · Motion Lab") and ends the tab title, which names what is on screen ("card – Jane Street · Motion Lab"; `lab/lib/project.ts`). **No controls in the component view.** A designer doesn't tweak duration or easing there: a motion change is a **new version** (fork, edit the version file, compare). The component view plays, replays and compares versions, and shows what each uses. The sidebar panels are accordions (native `<details>`): **Version** (the version tabs, lineage, Replay and the state controls) is the only one open by default; **Details**, **Tokens Used**, **Version history** and **Generated code** follow, closed. The **Compare with** panel is built but **switched off** (`SHOW_COMPARE` in `lab/main.ts`; the hidden section and its logic stay). **Details** is everything about the open version in one place: a list with **Component status**, **Plays**, **Reduced motion** and **Playback**. The plain-language **What it does** list (interaction versions) is built but **switched off** (`SHOW_WHAT_IT_DOES` in `lab/main.ts`, too busy for now); its logic (`summarizeInteraction`) and tests stay so it can come back somewhere else.
**Playback and runtimes.** `playbackOf(version, raw, { playbackRate, reducedMotion })` in `lab/lib/motion-models.ts` is the CSS runtime: a tween plays its keyframes with the easing curve over its duration; a **spring version** (authored with `properties[]` and a `bounce`) plays its from/to values as two keyframes with the easing curve, and the Playback row says so. `motionArgsOf(version, raw, …)` in `lab/lib/motion-args.ts` translates a version into Motion's terms and **always returns a spring** (`type: 'spring'`, the duration token as Motion's `visualDuration`, seconds): a spring version uses its own `bounce` (a bounce token or a number) and **every other motion (tweens, layers) uses the global bounce setting**; no easing curve is used anywhere under Motion. **Global bounce**: a select on the **Tokens view's Bounce tab** (a tab that shows only under Motion), listing the bounce tokens and nothing else (default `bounce.25`, Motion's own default); it persists in the URL (`?bounce=50`) and the tab, and every view reads it when it plays. A spring has no in-between frames, so it plays each property from its first value to its last (a tween with frames between says it skips them). `lab/lib/runtime.ts` holds the `Runtime` type and `PlayHandle` (speed, time, cancel, whatever runs the motion), so the speed control, replay and compare work the same on both. The Settings switch persists in the URL (`?runtime=motion`, absent = CSS) and in the tab (sessionStorage) so it survives links between views; it applies to the component, page and library views and Compare. Reduced motion is the short opacity-only fade under both (a spring with no bounce under Motion). The Version panel's **Playback** row says what is playing (CSS: `Easing · productive-entrance, 220ms`; Motion: `Spring · bounce 0.25 (bounce.25), 220ms (authored as easing; bounce is the global setting)`). **The runtime never changes exports**: Generated CSS, `spec.md` and `tokens.css` are the version as authored. A stale `?play=spring` in a URL is ignored.
**Tokens used**: what each motion of the open version uses, and **where in the motion** each token sits: its duration, easing and delay, a stagger that is a token, and the tokens its keyframes name (`0% transform`). A version with layers gets a group for the root and one per layer, so you can see the card's tokens apart from its text's. **It follows the runtime**: under Motion nothing plays an easing (every motion is a spring), so no easing token is listed and there are no pairing warnings; duration, delay, stagger and keyframe tokens still are, plus the **bounce token** each motion plays with (its own, else the global setting; a plain-number bounce is flagged as hard-coded). Under CSS it lists everything. Pairing warnings show under it. `getStepRefs(version, raw, runtime?)` (per motion), `getTokenRefs` (the whole version, as authored: what exports) and `pairingWarnings(version, raw, runtime?)` (per motion), `getTokenRefs` (the whole version) and `pairingWarnings` are in `lab/lib/token-refs.ts`; the Tokens view uses the same index for each token's "used by".
**Tokens view**: `/?view=tokens`. Tabs for duration, easing, distance, scale, opacity and delay (with the **default stagger** setting above its table), plus **bounce under Motion only** (the **global bounce setting** above the table, and three rows with a spring curve drawn from Motion's own spring generator, `springCurve` in `lab/lib/curve.ts`); tokens run smallest to largest (easings in system order: productive standard, entrance, exit, then expressive, then linear). **The columns are the spec sheets': Token, Value, and an Example where the kind has one** (easing: the curve drawn as the kit's easing sheet does, a dashed box, the straight line and a bezier's two handles; duration: a bar as long as the duration against the longest, plays on click; distance: a square that moves that far on click; bounce: the spring curve; scale, opacity and delay have no example). The Value header names its unit (`Value (ms)`, `(px)`, `(%)`). **Names are written the sheet's way: words joined by hyphens (`duration-300`, `distance-24`) and an easing without its group word (`productive-standard`)** (`tokenDisplayName` in `lab/lib/token-names.ts`). This is display only: token paths stay `duration.250` in files and in the Figma collection, and the row's tooltip shows the path (`Path: duration.250`) with the notes, status, value, usage and old names. Easings are grouped under 24px sub-headers (productive, expressive, linear).  The curve maths is in `lab/lib/curve.ts`.
**Motion table**: **switched off for now** (`SHOW_MOTION_TABLE` in `lab/main.ts`, or `?motionTable=1` to see it; it is built and tested but not rewritten on every change while designers ideate), and a **Generate spec** button sits in the top bar beside Replay (disabled until it is wired to write `spec.md` and the code). When shown it is under the preview in the component view (and as the "Motion table" section of `spec.md`, the same rows as a Markdown table with the timeline drawn as text), the open version written out the way a designer documents it by hand (the kit's modal sheet, the Jane Street motion docs): a black header with the component's name, then a section per part of the motion (`entrance`, and for a version with states one per state it goes to, named as the kit's button sheet names them: `hover on` and `hover off`, `focus on`, `pressed`, a click-driven state by its name (`open`); there is no "back to default" section (the way back is `hover off` when a hover trigger leads away, otherwise it has none, and a closing motion will be an `exit` when exits are documented) (`stateHeading` in `lab/lib/motion-table.ts`)) with a table of one row per property an element moves (Element, Property, From, To, Easing, Duration (ms), Delay (ms), Also) and a timeline of bars on a ms ruler. An element that uses an entrance preset gets a row in a preset table instead (Element, Preset, Delay (ms), Also: each track's timing and the stagger). Values are resolved (`translateY(16px)`, the authored `translateY({distance.20})` is the chip's tooltip), easings and tokens use the Tokens view's names, and **it is the version as authored, so it does not change with the CSS / Motion runtime**. A spring says so under Also with its bounce. The data is pure and tested in `lab/lib/motion-table.ts` (`motionTableOf`); `renderMotionTable` in `lab/main.ts` draws it.
**Pages**: `page.json` defines an ordered list of component instances for page-level motion review. **Page stagger uses delay tokens, never a free number** (`lab/lib/stagger.ts`): the page view's Stagger panel is a select of `Default (delay.80)`, `None` and each delay token (a page's own choice is `?pageStagger=none|120…`, absent = the default). The **default stagger** is a setting like the global bounce: a select on the **Tokens view's Delay tab**, delay tokens only, default `delay.80`, persisted in the URL (`?stagger=120`, a token label; anything else, such as an old millisecond link, falls back to `delay.80`) and the tab. Component *k* of the page starts *k* × the stagger token after the first; the Tokens view tooltip says which delay token is the default page stagger.
**Page versions**: a page version is a named combination for one page: which version of each component plays in each slot (`motionMap`, keyed by the page's component ids) and the page stagger (`stagger`: `none` or a delay token; absent = the default setting). It lives with its page, `pages/<page>/versions/v1.json`, `v2.json`, … (next free integer, like component versions; `forkedFrom` optional), and **points at component versions, copying nothing**: improving a component version improves every page version that uses it, and approval stays at the component level. A page with no saved version plays an implicit "Default" (every component's default version). The Page view's **Page versions** panel picks the version (`?pv=v2`), **Compare with** plays two saved versions side by side (`?compare=v3`; each column has its own stagger; the two pages are zoomed down to fit the window, never up, each column says its scale, and **Actual size** (`?size=actual`) shows both at their own size and scrolls sideways), and what is changed on screen (`?mm=…`, `?pageStagger=…`) is **unsaved** until **Save as new version**, which writes the next file through the dev server's `/__lab/page-version` (`scripts/page-version-plugin.ts`, same safeguards as the scale endpoint: dev only, same origin, one new file, never replaces one; a built copy disables the button, and Claude can call `savePageVersion` in `scripts/page-version-save.ts`). Choosing a version drops unsaved changes. **The page sits in a fixed-height window you scroll, like a browser window** (`--page-preview-height`, at most 760px), so a version's trigger can be felt: a version with `trigger.on: 'in-view'` (`scrollTriggerOf` in `lab/lib/scroll-trigger.ts`) waits, hidden, until its section enters the window by its `threshold` (0 when it names none) and then plays, once (`once` true, the default) or every time it enters again; a version with no trigger specified, or one a scroll cannot fire (`load`, `hover`, `click`, `route-change`), plays at load as before. The sections already in view as the page opens start together, staggered by their place; one that scrolls in later plays on its own with no stagger. Each Motion Map slot says "· plays on scroll" for such a version, **Replay All** scrolls back to the top and starts the page over, and in Compare each page has its own window. A page component with `layout: 'aside'` (a side menu) sits at the left of the page, full height and sticky as the window scrolls, with the other sections stacked in the column beside it (set the page's `width` to the aside plus the column). A page's optional `width` (px) is the width it is shown at (default 400, a column of cards; an imported page sets its Figma content width and its sections sit flush). **One page is always shown at its exact size, never scaled, 1:1 with the Figma frame**: its window is the page's own width edge to edge (no padding or border, flush with the lab's edges) with the detail panels to its right as one column when the lab window is wide enough for both and under it, in a row, when it is not, so a page as wide as the browser window shows whole: motion is judged at the size it ships (a 16px rise is 16px) and the lab is not responsive, so a window narrower than the page scrolls sideways; only Compare scales, because two pages cannot sit side by side at full size. The logic is pure in `lab/lib/page-versions.ts` (`validatePageVersion`, `resolveMotionMap`, `checkPageVersions`, `pageVersionsOf`); `tests/unit/pages.test.ts` checks every page and its saved versions against the components. This replaces the old `motion-maps/` presets (a preset had no page and did not save the stagger); the **entrance presets** (the Presets view) are unrelated. ## Naming conventions

- **Components**: `kebab-case` folder names (e.g. `card`, `hero-banner`)
- **Motion versions**: `v1`, `v2`, `v3` — sequential integers, never skip
- **Token paths**: dot notation, group first, no `motion` root, value-named except easing (e.g. `duration.250`, `easing.productive-standard`, `distance.20`)
- **Page IDs**: match folder name (e.g. `pages/home/page.json` has `"id": "home"`)
- **Page versions**: `v1`, `v2`, `v3` — sequential integers, never skip, the file is `pages/<page>/versions/<id>.json`
- **Page slots** (component ids on a page): the component name when used once, `<component>-1`, `<component>-2` when repeated

## How to add a new component

1. Create `components/<name>/` directory
2. Add `markup.html` — the component's HTML structure. Add `data-motion-target` to the element that will animate, and `data-motion="<layer>"` (kebab-case) to any inner element a version should move on its own (the title, the text…).
3. Add `styles.css` — component styles using CSS variables from tokens
4. Add `versions/v1.ts` — one file per version, exporting `v1` as a `MotionVersion` (see "How to add a new motion version").
5. Add `motion.ts` — it defines no versions itself; it only re-exports the files in `versions/`, plus the `versions` array and `defaultVersion` string. Every component, hand-built or imported, uses this structure:
   ```ts
   import type { MotionVersion, ComponentModule } from '../../lab/lib/types.js';
   import { v1 } from './versions/v1.js';
   export { v1 };
   export const versions: MotionVersion[] = [v1];
   export const defaultVersion = 'v1';
   const module: ComponentModule = { versions, defaultVersion };   // add status: "review" etc. when the component moves on (absent = in-progress)
   export default module;
   ```
6. Register it in `lab/main.ts`: import the module and call `registerComponent('<name>', module)`
7. Copy the test template: `cp tests/unit/_template.test.ts tests/unit/<name>.test.ts` and fill it in
8. Copy the E2E template: `cp tests/e2e/_template.spec.ts tests/e2e/<name>.spec.ts` and fill it in

## How to add a new motion version

1. Create `components/<name>/versions/v3.ts` (next free integer) exporting the new version. Never define a version inside `motion.ts`; `tests/unit/version-files.test.ts` fails if you do.
   ```ts
   import type { MotionVersion } from '../../../lab/lib/types.js';
   export const v3: MotionVersion = {
     id: 'v3',
     label: 'Descriptive Name',
     model: { model: 'tween', duration: 'duration.250', easing: 'easing.productive-standard' },
     keyframes: [ /* only motion properties */ ],
     forkedFrom: 'v1',        // the version this was copied from (required)
   };
   ```
   Every version needs lineage: `forkedFrom` (a version id in the same component) or, for an imported v1, `lineage: 'imported from <source>'`. `forkVersion(parent, id, label)` in `lab/lib/version-meta.ts` builds a new version that way.
2. In `motion.ts`, import and re-export it, and add it to the `versions` array
3. **Versions may only change motion properties**: `opacity`, `transform`, `filter`, `clip-path`. Never use `display`, `position`, `width`, `height`, or any structural property in keyframes. **One exception: an interaction's states and layer states may also set `width`, `height`, `grid-template-columns`/`rows`, `column-gap` and margins** (never `display`, `position`), so a cell can really resize and its neighbours give way (the mosaic morph); give every state a value for each such property, as none has a natural one. CSS interpolates these with equal track counts and the same units (px, not fr).
4. Add unit tests for the new version in `tests/unit/<name>.test.ts`, including `validateVersionMeta(versions)`

### Component status and lineage

- **Approval is the component's, not a version's.** A component's `motion.ts` may set `status` on the module: `'in-progress' | 'review' | 'approved' | 'archived'` (absent = `in-progress`; unknown values fail `validateVersionMeta(versions, status)`). A version file has **no** `status` (it fails validation as a disallowed property). Versions are just the explorations; which one ships is decided by approving the component, and the approved version is its **latest**.
- Shown as a badge on the library cards (not for in-progress) and as the **Component status** row in the component's Details. The library has the status filter; **archived components are hidden by default** and appear with "Show archived" (URL: `?status=…&archived=1`). The component view and the Motion Map have no status filter and no version badges.
- `npm run spec` with no version exports the component's **latest version** when the component is approved; with a version id it exports that one whatever the status, and `spec.md` says "Component status: …".
- `forkedFrom` must name an existing version of the same component; a version with neither `forkedFrom` nor `lineage` fails `validateVersionMeta`.

### Trigger and reduced motion (developer hand-off)

The lab plays motion on demand, so two things a developer needs live in the version file instead:

```ts
trigger: { on: 'in-view', threshold: 0.2, once: true },  // when it plays in production
reducedMotion: 'fade',                                   // what prefers-reduced-motion visitors get
```

- `trigger.on`: `'load' | 'in-view' | 'hover' | 'click' | 'route-change'`. `threshold` (0–1) is for `in-view` only; `once` says first time only (`true`) or every time (`false`). **Absent = not specified**: the spec and the Generated CSS say so, they never guess one. Ask the designer when they haven't said; don't invent it. Imports don't set it.
- `reducedMotion`: `'fade'` (absent = fade: transforms dropped, opacity fade of at most 150ms, `REDUCED_MOTION_FADE_MS`) or `'none'` (no animation, end state shown). The lab's playback and the exported CSS follow the same rule, so what a designer sees under reduced motion is what ships. Versions with no opacity change get no animation under `'fade'`.
- Both validate in `validateMotionVersion`, show in the component view ("Plays", "Reduced motion"), and carry through `forkVersion`.

**Generated CSS and spec export.** The "Generated code" panel (CSS, GSAP or Motion) and `npm run spec` share one generator (`lab/lib/css-output.ts`): plain, stack-neutral CSS with named `@keyframes motion-<component>-<version>`, a `.motion-<component>-<version>` class, token custom properties with the literal value as fallback (`var(--motion-duration-300, 300ms)`, delays too: `var(--motion-delay-70, 70ms)`, so changing a token changes the motion), a stagger index (`--motion-index`) and a `prefers-reduced-motion` block. A version authored as a spring exports its from/to values with its easing (CSS has no spring), with a comment saying so.

`npm run spec -- <component> [version] [--out <dir>] [--format css|gsap|motion|all] [--bounce <N>]` writes `export/<component>/<version>/` (gitignored) with `motion.css`, `tokens.css` and `spec.md` (`lab/lib/spec.ts`), plus `motion.gsap.js` and/or `motion.motion.js` with `--format` (`all` for both). **Export formats** (`lab/lib/export-code.ts`): **CSS** is the baseline; **GSAP** is the same motion as a timeline, easing only (seconds, `CustomEase.create` for each easing token, layers as timeline positions, `stagger` as the timeline delay, a reduced-motion branch; GSAP has no springs, so a spring version plays its easing and the code says so; transforms become `x`, `y`, `scale`, `rotation`, and one that can't convert is listed in a comment); **Motion** is the same motion with every motion a spring, built from the same `motionArgsOf` the lab plays under Motion (the version's own bounce token, else the global bounce: `--bounce 50` sets it for the file, default 25). Each is a `play<Component><Version>(el, { index })` function. The Generated CSS panel has a **Format** picker (CSS / GSAP / Motion) showing the same code. **Exports never follow the runtime.** `gsap` is a dev dependency, used only by a unit test that runs the generated GSAP code and checks its timeline against the CSS timing (duration, delay, stagger, every layer). No version = every approved version; an explicit version exports whatever its status and says so in `spec.md`. For a version whose trigger is `in-view`, `spec.md` also gives the `IntersectionObserver` that adds the classes (its threshold, first time only or every time, each layer's classes, and the GSAP/Motion function to call instead): the CSS does nothing until they are added. `spec.md` also lists what the lab can't verify: the production element, layout and environment, and performance.

## Token types

Tokens are **primitives only**: no composite tokens, no component-specific names. A motion step names its primitives directly, a duration plus an easing (`duration.250` + `easing.productive-standard`).

| Kind (group) | `$type` | Names | Values | CSS variable |
|---|---|---|---|---|
| `duration` | `duration` | `50 100 150 200 250 400 700 1200` | ms | `--motion-duration-250` |
| `easing` | `cubicBezier` | `productive-standard/-entrance/-exit`, `expressive-standard/-entrance/-exit`, `linear` | `[x1, y1, x2, y2]` | `--motion-easing-productive-standard` |

Gesture **thresholds** are part of the system but have no tokens here yet (no values were supplied).

Scale kinds are **named by their value** (`duration.250` is 300ms, `scale.95` is 95%); **easing is the one semantic layer**. Token paths use dot notation with no `motion` root; CSS variables add a `motion` prefix and drop the dots, so they can't collide with other custom properties.

**Figma mapping.** `tokens/motion.json` is shaped like the Figma variable collection it mirrors: the file is the collection (no root group) and each group is a variable group, so `easing.productive-standard` here is `easing/productive-standard` in Figma (dots become slashes). Keep names identical in both so the sync (see PLAN.md) is a straight copy. **A global scale renames tokens, so the sync must rename the existing Figma variables in place, not delete and recreate them** (recreating loses every binding in the design files): each renamed token lists its previous names in `$extensions.oldNames`, which is how the sync finds the variable to rename. Opacity and scale tokens are numbers (`0.04`, `0.95`) named by their percent (`opacity/04`, `scale/95`). The collection's description should say which scale the tokens follow (`$extensions.scale`), or Custom.


**Pairing rules** (warnings, never errors; `pairingWarnings`): productive easings pair with 50–300ms, expressive easings with 400–1200ms. Shown under "Tokens used".

**Status.** Every token is `system` (approved) or `experimental`, in `$extensions.status`. A token with no status is experimental, as **new tokens start experimental**. **A renamed or merged token keeps the highest status of the tokens folded into it** (system outranks experimental). Notes are `$description`; old names are `$extensions.oldNames` (shown with usage in the Tokens view tooltip).

**References in keyframes.** A tween keyframe value may name tokens: `translateY({distance.20})`, `{opacity.100}`, `scale({scale.95})`; a leading minus negates one (`translateY(-{distance.20})`, the "-distance-N" form). Playback resolves them to values (`resolveKeyframes`); the CSS export writes `var(--motion-distance-16, 16px)` and `calc(-1 * var(…))` for a negative; they count as usage. An unknown reference throws. Spring `properties[]` `from`/`to` are still plain numbers.

**Interactions (all 6 steps done: the model, the lab firing real events, the card example, and the plain-language summary).** A version can describe a component's **states and the transitions between them** instead of one entrance, so hover, press, focus, click and open/close can be played: `interaction: { initial, states, transitions, layers?, triggers? }` (`lab/lib/types.ts`). **Triggers** say what moves it between states and are **declared in the version, never in the markup** (a re-import of the Figma frame replaces the markup): `{ on: 'hover' | 'press' | 'focus', state, target? }` goes to `state` while it lasts and back to the state it was in when it ends (it cannot go to the resting state); `{ on: 'click', set: state, target? }` goes to a state and `{ on: 'click', toggle: [a, b], target? }` swaps; `{ on: 'arrows', states: [a, b, c] }` steps through the states with the left and right arrow keys, left to right, stopping at the ends (heard on the whole page, not while typing in a field or with a modifier); `target` is the `data-motion` name of the element the event is listened on, the component's root when left out; two triggers for the same event on the same element are refused. A trigger on an element outside the component (a button elsewhere that opens a panel) is the developer's to wire, and the spec says so (step 5). **Layers**: `layers: { image: { states: { hover: { transform: 'scale({scale.100})' } }, transitions?: {…} } }` gives a layer of the component its own values (and optionally its own timing) for the states, so a hover can lift the card while the image scales; a property a state leaves out is at its natural value there (opacity 1, no transform: `NATURAL_VALUES`; any other property must be given in every state; `partValues`, `timingFor`, `interactionParts` in `lab/lib/interaction.ts`). **`model` is optional** on an interaction version: `modelOf(version)` derives one from its first transition (a tween with that timing) for the panels that expect one, and `stepsOf` carries it (`EntranceVersion` is a version that certainly has a model, what the playback, CSS and export code works on). **States are named in the kit's words** (`default` for the initial state, then `hovered`, `pressed`, `focused`; the card's v2 is the example): where this page says "the rest state" or "rest" it means the initial state, and the generated spec and CSS now call it `default`. A **state** is a set of motion properties (opacity, transform…, token references allowed, no structural properties); a **transition is named by the state it goes TO** (`transitions.open`, `transitions.closed`), because that is how CSS, GSAP and Motion all take their timing, at the moment you move to a state. Each transition is a tween or a spring (a bounce token or number) with its own duration and easing, so going to `open` can bounce while going to `closed` is a plain exit (`productive-exit`; expressive exits paired with a short duration trip the pairing rule). (A model is no longer needed: see above.) Pure maths and plans are in `lab/lib/interaction.ts` (`validateInteraction`, `cssTransitionPlan`, `motionTransitionPlan`, `motionStates`, `describeTransition`); `lab/lib/transform.ts` splits a transform string into x, y, scale, rotate for Motion; the DOM side is `lab/lib/interaction-player.ts` (`createInteractionPlayer`: knows the current state and moves the element to another from wherever it is NOW; sets `data-state`). **In the lab** the Version panel shows a button per state, Toggle and **Interrupt** (go to the next state, then back after 150ms, before it arrives), and a click on anything marked `data-motion-set="<state>"` in the markup moves the component (the side panel's × is `data-motion-set="closed"`); Replay resets to the rest state and goes to the next one; the Playback row says what plays into each state under the current runtime; Tokens used groups tokens per transition ("into open duration") and per state ("closed transform"). **Exports:** CSS is the rest state as the class and every other state as `[data-state="…"]`, each carrying the timing into it, with a reduced-motion block (opacity still fades, movement snaps); GSAP is `states`, `transitions` and `goTo<Component><Version>(el, state)` with `overwrite: "auto"`; Motion is springs into each state. **Findings from the spike** (details in PLAN.md): Motion's duration-based springs (`visualDuration` + `bounce`) retarget from the current value but **ignore the speed of the move they cut short** (Motion's source says so; a measured −233px/s passed as `velocity` changed nothing), so velocity carry-over needs physics springs (stiffness, damping, mass); CSS retargets from the current computed value and loses the speed too; Motion's `duration: 0` instant sets are unreliable on first use, so the player sets with `duration: 0.001` and waits for it. **The lab fires the triggers for real** (`attachTriggers` in `lab/lib/interaction-player.ts`, attached wherever the component is shown: component view, page view, library): hover on `pointerenter`/`pointerleave` (a touch pointer never hovers), press on `pointerdown` until `pointerup`/`pointercancel` anywhere (the primary button only), focus on `focusin`/`focusout` for keyboard focus (`:focus-visible`) on the element or anything inside it, click on `click` (set a state, or toggle between two). **Holds**: a hover, press or focus *holds* the component in its state while it lasts; with several at once the latest wins, and when one ends it goes to the one beneath it or to the **base** state (the resting one, or what a click or the stage's buttons last set), so press-then-leave ends at rest, not at hover; going to a state with the stage's buttons makes it the new base and clears the holds. The player moves the root and every layer that has values (`data-motion="<name>"` elements inside it; a layer with no element in the markup is skipped) with the layer's own timing, from wherever each is. Stage behaviour: a version with hover, press or focus triggers **starts at rest** so it can be hovered, and **Replay** shows a hover-and-leave (goes to the first other state, then back to rest after 700ms); a version with only clicks (the side panel's open/close) plays its first move on load. An interaction's optional `hold` (a token or a time like "1000ms") makes it rest in the initial state for that long first, so a starting view is seen before the opening move plays (a replay restarts the wait; after an entrance, the wait starts when the entrance ends). The side panel's × closes it through its declared `click` trigger on the `close` layer; the old `data-motion-set` markup hook is gone. **Examples:** the side panel's v2 "Open / Close" (states only, click) and the card's v2 "Hover Lift" (v1's entrance, then rest, hover: lifts 4px, pressed: 98%; hover and press triggers). A layer with its own values and timing for the states (an image that scales on hover) is `interaction.layers`; no shipped version uses it now, the unit tests do. Tests: `tests/e2e/interaction-triggers.spec.ts` wires every event on stand-in elements (hover, touch ignored, press held and released elsewhere, right-click ignored, keyboard focus, click set and toggle, a layer target, detaching, a missing layer), and `tests/e2e/interactions.spec.ts` plays the card under both runtimes. **"What it does"** (Version panel, interaction versions only; `summarizeInteraction` in `lab/lib/interaction-summary.ts`, pure) says each trigger in plain words, with every part's change against rest and its timing under the current runtime (CSS: ms and easing name; Motion: ms and bounce), how the return to rest goes, and lists states no trigger leads to as set from outside. The Playback row also lists a layer's own timing (`describeTransition` takes `target`). **Trigger-aware exports (step 5).** **CSS**: rest is the class; every state is also `[data-state="…"]` (for a click or a script); hover is `:hover` inside `@media (hover: hover)`, press is `:active`, focus is `:focus-visible` / `:has(:focus-visible)`, a trigger on an inner element is `:has([data-motion="x"]:hover)` on the root; each layer is a descendant rule (`.base:hover [data-motion="image"]`) with its own timing; later rules win (focus, hover, press), the rest rule carries the way back, and the reduced-motion block lists every selector. **GSAP and Motion**: `parts` (the component, then each layer, each with `states` and `transitions`), `setup…(el)`, `goTo…(el, state)` (one tween/animation per part: an array when there are layers, one otherwise) and **`attach…(el)`**, which wires the declared triggers with the lab player's rules (touch never hovers, a press lasts until released anywhere, keyboard focus, latest hold wins, base returns) and returns a function that removes the listeners. **spec.md** has a Triggers table (event, element, what it means, what happens) and names the states set from outside the component, plus layer states and layer timing. Tests: `tests/unit/interaction-exports.test.ts` (including running the generated GSAP `attach` on stand-in nodes) and an e2e test that uses the exported CSS alone on a plain element. **A version can appear and have states** (an entrance plus hover, press, focus, click): give it a `model` (with `keyframes` or spring `properties`, and `layers`, as in any entrance) **and** an `interaction`; `hasEntrance(version)` (`lab/lib/motion-models.ts`) is "has a `model`". The two halves stay apart: `stepsOf` returns only the entrance's motions when there is a model, `getStepRefs` adds a **states** group after them, `pairingWarnings` covers both, and the entrance's `trigger` (when it plays) is separate from the interaction's triggers. **Sequence, not mix**: the entrance plays first; the states do not respond until it ends. In the lab (`playEntranceThenStates` in `lab/main.ts`) the player is locked (`player.setLocked(true)`: hover, press, focus and click do nothing, nothing is held), the entrance plays (`PlayHandle.done` settles when it ends), then the entrance's animations are released (CSS), the player resets to the rest state (the entrance should end where rest begins: `opacity: 1`, no transform) and unlocks; Replay restarts from the entrance's first frame. **Exports:** CSS puts both on the one class (add it when the entrance trigger fires; `animation-fill-mode: backwards`, not `both`, so after the entrance the rest state and its transitions apply; a hover during the entrance takes effect when it ends); GSAP and Motion files have `play…(el)` (the entrance) and then the states (`setup…`, `goTo…`, `attach…`), with the hint `playX(el).then(() => attachX(el))` (Motion: `Promise.all(playX(el)).then(…)`); spec.md has "On appear" sections before the Triggers/States. **What it does** starts with an "Appears" line, and Playback lists `appear: …` (and `title appear: …`) before each `into <state>`. The designer-facing rules are under "Designing states and triggers with a designer" in the Designer workflow; later: drag, Compare for interactions, and the Figma-variant import.

**The base tokens (Vitrine).** The template's starting set follows the Vitrine UI kit and is deliberately small. **Duration** is the kit's `50 100 150 200 250 400 700` plus `1200` (the longest moves keep a token). **Distance** and **delay** follow the **Fibonacci** scale (distance `4 8 12 20 32 52 84 136`, delay `40 80 120`, recorded in `$extensions.scale`). **Scale** is just `90 95 100` (percent: 0.9, 0.95, 1) and **opacity** just `0 100` (0 and 1). Easing and bounce are unchanged. Duration, scale and opacity are set by hand (Custom); distance and delay are generated. The set was moved onto these from the earlier one with `npm run tokens:remap -- tokens/migrations/vitrine-base.json` (below), which sent each old token to the nearest new value (`duration.220` became `duration.200`, `distance.16` became `distance.20`, `scale.98` became `scale.95`) and recorded the old names, so the Figma sync renames in place. The renames are in `tokens/migrations/vitrine-base.renames.json`: **a project repo that merges this change runs `npm run tokens:remap -- --renames tokens/migrations/vitrine-base.renames.json` to rewrite its own version files, presets and page versions** (its `tokens/motion.json` already has the new tokens from the merge). `npm run tokens:remap -- <spec.json>` (`lab/lib/token-remap.ts`) is also how to set a kind to a list of your own: each kind is a `scale` (a global scale's values), `values` (whole ms or px) or `tokens` (named number tokens), with `overrides` (old name → new name) where nearest value is not what is wanted; `--dry-run` shows the renames and writes nothing.

**Global scale.** One setting decides how the values of the `distance`, `duration`, `delay`, `opacity` and `scale` tokens are calculated, from a ratio taken from typography (or Fibonacci): **minor third** (6:5), **major third** (5:4), **perfect fourth** (4:3), **golden ratio**, **Fibonacci**, or a custom ratio above 1 such as `1.4`. Easing and bounce are not part of it. The tokens stay value-named, so a scale gives different names (`distance.12` is 12px), and the values are still written into `tokens/motion.json`: the Figma variable collection mirrors that file, so the sync stays a straight copy. **It is opt-in**: a file with no recorded scale is **Custom** (its values were set by hand, which is the default), because applying a scale renames tokens.

- **The maths** (`lab/lib/scales.ts`, pure): `deriveKind(kind, scaleId, options)` returns the tokens (name = value, `$type`, `$value`) a scale gives one kind. Distance, duration (base 100ms, 8 steps), delay (base 40ms, 3 steps) and opacity (base 4%, 8 steps) are base × ratio^n, rounded; opacity drops steps above 100%, and distance can snap to a grid (`--snap 4`). `scale` moves around 100% in quarter-powers of the ratio (major third: 85, 89, 95 and 106, 112), and Fibonacci uses the golden ratio there. The counts match the token file, so changing the scale keeps the same number of tokens.
- **Anchored on 4px.** Most projects build on a 4px unit, so distance starts at 4px (`BASE_UNIT_PX`). Only scales that give distinct whole values from there are offered: the major second (4, 5, 5, 6…) was removed for colliding, and a test holds every scale to distinct, increasing values and names for every kind at its defaults. If two steps still round to the same value (a base that is too small for the ratio), it throws and says how to fix it; nothing is written.
- **Durations follow the scale**, so the pairing rules (productive 50–300ms, expressive 400–1200ms) are warnings against whatever values a scale gives: no scale reaches today's 1200ms top step, so expect some.
- **Applying keeps what the tokens already say.** Step i takes over from the old step i (matched by rank): it keeps that token's status and notes and records the old name in `$extensions.oldNames`; extra steps start experimental; folded steps keep the highest status. The renames are followed through the version files, so nothing dangles. Matching by rank means a scale with different spacing moves a token's *value*: the old `scale.100` becomes the new fifth step, not a 99%.
- **The recorded scale.** The scale used for each kind is saved at the root of the token file, `$extensions.scale.kinds` (`readScaleConfig` / `withScaleConfig`, `lab/lib/scale-apply.ts`). Never edit it by hand; applying a scale writes it.
- **Settings panel** (`lab/lib/scale-settings.ts`): the gear in the header, on every view, opens Settings (the theme, the motion library and the Global scale), since this is something you change rarely. It says what the tokens follow now (or Custom), has a select of the scales, a summary ("Major third would rename 29 tokens and change 7 version files"), a foldable "What changes" with each current token beside the one that takes its place and the versions that use it, an **Apply button** and the command for doing it by hand. Previewing writes nothing and agrees with the generator, because both use the pure code in `lab/lib/scale-apply.ts` (`applyScale`, `previewScale`).
- **Apply** asks first ("This renames 29 tokens in tokens/motion.json and edits 7 version files. Save your work first so you can go back."), then POSTs the scale to the **dev server's `/__lab/scale`** (`scripts/scale-plugin.ts`, a Vite plugin that exists only under `npm run dev`, never in a build), which calls `runScale` in `scripts/scale-run.ts`, the same code the command line uses. The endpoint accepts only a known scale (or a ratio above 1), writes only `tokens/motion.json` and the version files, works everything out before writing (a scale that doesn't fit changes nothing), and refuses a request whose Origin isn't the server's own. The files changing reloads the page, which comes back with Settings open and a one-time note of what changed. A built copy has no endpoint, so the button is off and points to the command.
- **Tests never apply for real.** The e2e tests answer the Apply POST themselves, and `tests/e2e/settings.spec.ts` refuses any apply that isn't a dry run unless a test set up its own reply, so a test cannot rewrite the real token file. If `tokens/motion.json` or a version file changes during a test run, something got through: restore them from the last save and find out why before going on.

**Using the scale (for Claude, with a designer).** A scale is a project-wide decision, not a tweak: **do not apply one unless the designer asks**. When they do, preview it first (Settings, or `--dry-run`) and say what it does in design terms ("Major third makes the spacing steps 4, 5, 6, 8, 10… and renames 29 tokens across 7 versions. Want to see how the durations change too?"), make sure their work is saved first, then apply (the button, or `npm run tokens:scale -- --all <scale>`). Afterwards run `npm run check`: tests, notes and any code that names a token by its old value (`distance.20`) may need updating, and the pairing warnings may have changed. Then say that the Figma variables need syncing (see "Figma mapping" under Token types).


**The command.** `npm run tokens:scale -- <distance|duration|delay|opacity|scale> <scale> [--base N] [--steps N] [--up N] [--snap N] [--dry-run]` and `npm run tokens:scale -- --all <scale>` (`scripts/scale-tokens.ts`) regenerate one kind, or all five, from a scale (see the file header). `--all` derives every kind before changing anything; `--dry-run` prints the new names and every rename and writes nothing; `--root <dir>` works on another checkout. Not for `easing` or `bounce`. Review the diff afterwards: pairing rules, keyframes and tests that name tokens may want a second look.

The token compiler (`lab/lib/token-compiler.ts`) reads `tokens/motion.json` and returns `{ cssVars, raw, meta }`: the CSS custom properties applied to `:root` at startup, a flat `raw` map by path for the motion models, and each token's notes, status and old names.

## Motion model rules

### Tween model
```ts
{ model: 'tween', duration: 'duration.250', easing: 'easing.productive-standard', delay?: 'delay.40' }
```
- `duration` and `easing` are token paths, or literal values (`"300ms"`, `"ease-out"`, `"cubic-bezier(...)"`; a literal is flagged as hard-coded). `delay` and `stagger` may be delay tokens or literals.
- A tween plays its easing curve.

### Spring model
```ts
{ model: 'spring', duration: 'duration.250', easing: 'easing.productive-entrance', bounce: 0, delay?: 'delay.40', properties: [{ property: 'transform', wrapTransform: 'scale', from: 0.92, to: 1 }] }
```
- The same primitives as a tween, a duration and an easing, plus an optional **`bounce`**: a bounce token (`'bounce.50'`) or a number from 0 to 1. Without one it uses the **global bounce setting**, as every tween does. Under **Motion** it plays as a real spring: the duration is Motion's `visualDuration` (when it visually arrives) and the easing is not used. Under **CSS** it plays its from/to values with the easing curve over the duration. `resolveBounce(value, raw)` in `lab/lib/motion-models.ts` resolves it.
- **The lab simulates no springs** (the spring engine is gone). A real spring is only played by a library that has one: Motion. CSS (and a GSAP export, planned) are easing only.
- Spring versions declare `properties[]` instead of `keyframes`.

### Layers
```ts
{
  id: 'v4', label: 'Fade Up, Text Follows',
  model: { model: 'tween', duration: 'duration.200', easing: 'easing.productive-entrance' },   // the root
  keyframes: [ … ],
  layers: {
    title: { model: { model: 'tween', duration: 'duration.250', easing: 'easing.productive-entrance', delay: 'delay.80' }, keyframes: [ … ] },
    text:  { model: { model: 'tween', duration: 'duration.250', easing: 'easing.productive-entrance', delay: 'delay.120' }, keyframes: [ … ] },
  },
}
```
- A version moves the component's root (`data-motion-target`) with its own `model` and `keyframes`, and may move **layers** too: `layers` is keyed by the `data-motion` name of an element inside the root, and each layer is a `MotionStep` (`model` plus `keyframes`, a tween or a spring) with **its own duration, easing and delay**. That is how the text moves differently from the card.
- A layer shares the version's `stagger`, `trigger` and `reducedMotion`. Use `delay` (a delay token) to start a layer after the root. A layer name must be lowercase letters, numbers and hyphens; every element with that `data-motion` is animated.
- `stepsOf(version)` in `lab/lib/motion-models.ts` lists the root (name `null`) and then each layer, each as a version of its own, so timing, usage and CSS work on a layer exactly as on the root.
- CSS export: a layer gets its own `.motion-<component>-<version>-<layer>` class and `@keyframes`; `spec.md` has a "Layer: <name>" section for each. Playback cancels and replays the layers with the root, and the speed control reaches them.

### Entrance presets

A preset is a named, standard entrance (a fade and a rise, plus a scale for card and media), **the project's own data**, defined once in **`tokens/presets.json`** from the existing primitive tokens (it is **not** a token type; `lab/lib/entrance-presets.ts` only reads and checks the file). The template ships a default set and a project edits or replaces it: each preset is `{ rise, scale?, move: { duration, easing }, fade?: { duration, easing }, status?, description? }` naming tokens only (a distance, a scale, a duration, an easing), `status` is `system` (approved) or `experimental` like a token, and `separateFade: false` makes every preset one track. `parsePresets` refuses a malformed file with the preset and the problem, and `validatePresetTokens` (checked by `tests/unit/presets-table.test.ts` for any project) says which token does not exist or is the wrong kind; unknown preset names in a version are refused by `validateMotionVersion`, and the pairing rules apply to every preset. Where this fits: presets compose tokens that live in the Figma Motion variable collection, but Figma has no preset concept, so the recipe lives here and in the exported `presets/` files; do not author motion in presets that a component version could say. The Presets view shows each preset's recipe and status (a project's own preset names get a generic example element). The template's default six: **eyebrow, title, text** (fade 300 `easing.productive-entrance`, rise 16px 560 `easing.expressive-entrance`), **card** (rise 24px, from `scale.95`), **media** (rise 24px, from `scale.95`), **ui** (fade 100 `productive-entrance`, rise 8px 140 `productive-standard`). No scramble, no other properties.

```ts
{ id: 'v3', label: 'Cards rise', entrance: { preset: 'card', delay: 'delay.80' },   // the root element
  layers: {
    title: { preset: 'title', delay: 'delay.80', stagger: 'delay.40' },            // each title line starts 40ms after the one before
    text:  { preset: 'text',  delay: 'delay.120' },
  }, lineage: '…' }
```

- **Element + preset + delay (+ stagger).** `entrance` is for the root (use it **instead of** `model`/`keyframes`); a layer is either a motion (`model` + `keyframes`) or a preset step. A preset step takes only `preset`, `delay` and `stagger` (delay tokens; `stagger` offsets each matching element, for repeating elements such as title lines or grid items, and is separate from the version's `stagger`, which offsets sibling components on a page). Existing versions are untouched: presets are opt-in.
- **Two tracks, easy to make one.** A preset is up to two motions on the same element: the **fade** (opacity; a spring with `bounce.0` so under Motion opacity never overshoots; CSS plays its easing) and the **move** (a tween: rise and scale). `stepsOf` (`lab/lib/motion-models.ts`) expands a preset into entries with `track: 'fade' | 'move'` (or `'all'`), `preset` and `elementStagger`, so playback, Tokens used (groups named `title fade`, `title move`), pairing warnings, the summary and the exports all work from it. **To use one track:** set `SEPARATE_FADE = false` in `entrance-presets.ts` (every preset), or delete one preset's `fade` line (that preset): the fade then shares the move's duration and easing, in one tween with opacity and transform together.
- **The Presets view** (`/?view=presets`, the nav's Presets button): each preset as a card (its name at 16px, a light Replay, and a simple example on the page-colour canvas: eyebrow, title, text, card, media, ui), with Replay all as the page's one primary (black) button in the same top bar as the other views. The recipe (rise, move and fade tokens, status) is not printed on the cards: it is the tooltip on the name; the token values are in `tokens/presets.json`. It plays through the same entrance code as a component, so the CSS / Motion switch applies.
- **Exports: one shared definition per format, components use it by name.** CSS: `presets.css` (`@keyframes` per track and `.motion-preset-<name>`, delay from `--motion-delay`, `--motion-stagger` and `--motion-item`); the component's CSS only sets those variables on its own class (add both classes to the element). GSAP and Motion: `presets.gsap.js` / `presets.motion.js` with the `presets` table and `playPreset(target, name, { delay, stagger })` (Motion: springs, the move with the global bounce, the fade with none); the component's `play…(el)` calls `playPreset`. Under reduced motion presets play only the opacity fade (at most 150ms). **They belong to the project, not to a version: `npm run spec` writes them once, to `<out>/presets/`** (`presets.css`, plus the GSAP/Motion ones with `--format`) whenever an exported version uses one, a version's GSAP and Motion code imports them from `../../presets/`, and `npm run spec -- --presets` writes just those shared files (every format) with no component; the Generated code panel shows the shared definition above the component's code. `spec.md` names the preset per element. A preset version that also has `interaction` works like any entrance plus states (the root's preset animation uses `animation-fill-mode: backwards` in the CSS).

## Testing rules

**Every new component and version requires tests.** The basics are covered for every component and version in the repo without a test of its own: `tests/unit/all-versions.test.ts` (each version validates, has lineage, names only tokens that exist, follows the pairing rules) and `tests/e2e/all-versions.spec.ts` (each version plays in the lab with no console errors). A new version needs nothing more for those; add a test only for what is particular to it (a specific duration, a trigger, a layer). A new component also needs its own pair, from the templates:
```
tests/unit/_template.test.ts   → copy to tests/unit/<component>.test.ts
tests/e2e/_template.spec.ts    → copy to tests/e2e/<component>.spec.ts
```

### Unit test coverage required per component/version
- `validateMotionVersion(v)` does not throw (no structural keyframe props, no extra properties)
- Tween versions: `resolveTiming(v, raw)` produces a numeric `duration` > 0 (`resolveTiming` is tween-only and throws on spring versions; use `playbackOf`)
- Tween versions: `resolveTiming(v, raw)` produces a string `easing` containing `cubic-bezier`
- Token paths (e.g. `duration.250`, `easing.productive-standard`) resolve to expected concrete values

### E2E test coverage required per component
- Component renders visibly at `/?view=component&component=<name>`
- Each version plays without console errors

### Sample content and project repos

The template ships sample content so its own feature tests have something to run on: the `card` and `side-panel` components and the `home` page (`tests/samples.ts` lists them). **A project repo holds client content only, so it deletes these three** (`components/card`, `components/side-panel`, `pages/home`). Everything that needs them then skips itself, so a project's `npm run check` tests the project's own components and pages, and the template's feature tests stay in the template:
- `SAMPLES_PRESENT` is true only when all three exist. `vitest.config.ts` leaves out `SAMPLE_UNIT_FILES`, `playwright.config.ts` ignores `SAMPLE_E2E_FILES` and `npm run typecheck` (`scripts/typecheck.ts`, plain `tsc --noEmit` when the samples are there) leaves the unit files out of the type check when it is false; tests that need a sample in a file that is otherwise independent start with `test.skip(!SAMPLES_PRESENT, SAMPLES_NEEDED)` (`describe.skipIf` / `it.skipIf` in unit tests).
- **When you write a test for a template feature that uses a sample** (opens `component=card` or `page=home`, or imports from `components/card/`), list its file in `tests/samples.ts` or guard it as above: `tests/unit/samples.test.ts` fails for one that does neither. A test that needs *some* component should open the lab's default (`/?view=component`, `/?view=page`: the first component and page when the samples are gone) so it runs in a project too.
- The lab itself does not need the samples: with no `card` or `home` it opens the first component and the first page.
- **Customised presets work the same way.** `tokens/presets.json` is the project's own; the tests that pin the template's default presets (their names and values, and the CSS and code written from them) run only while the file is still the default (`TEMPLATE_PRESETS` in `tests/samples.ts`; `PRESET_UNIT_FILES` and `PRESET_E2E_FILES` are left out otherwise). Everything about the file's shape, its tokens and the pairing rules is tested for any project (`tests/unit/presets-table.test.ts`).

## Figma import

Components can be imported from a Figma frame instead of hand-built. The Figma MCP (design context, variables, screenshot, assets) is driven by the agent; the deterministic, file-writing half lives in `scripts/figma-import/lib.ts`. **Figma is read through the official Figma MCP/connector, always by link**: the designer pastes a frame link (⌘L in Figma; the `node-id` is in it), never "whatever is selected", which the connector can't see reliably. `get_variable_defs` returns only the variables one node uses, so a whole variable collection (the Motion tokens, a project's variables) is read or written with a `use_figma` script (`figma.variables.getLocalVariableCollectionsAsync()`). The agent writes a manifest JSON and runs `npm run figma:import -- <manifest.json>` (see the header of `scripts/figma-import/cli.ts` for the manifest shape).

### Import rules

- **Name**: kebab-case from the Figma layer name (`hero banner` → `hero-banner`). If the linked frame is a generic wrapper, name it from its only meaningful child.
- **Output**: `components/<name>/` gets `markup.html`, `styles.css`, `assets/`, `meta.json` (Figma url, file key, node id, import date, frame size, variables, assets, font fallbacks, designer-facing `issues`), and — first import only — `motion.ts` + `versions/v1.ts`.
- **Markup**: the root element has `data-motion-target`; every animatable layer has `data-motion="<layer-name>"`. Asset references are relative: `assets/<file>`. Never leave temporary Figma asset URLs (`figma.com/api/mcp/asset/...`) in the source.
- **Styles**: use CSS custom properties from Figma variables (`text/default` → `--text-default`). No hard-coded colors or spacing that a variable covers.
- **Variables**: merged across imports into `tokens/figma-variables.json`; `tokens/visual.css` and `tokens/fonts.css` are generated from it. Never edit those three files by hand.
- **Fonts**: licensed font files go in `/fonts` (gitignored). Files are matched to Figma typefaces by name; unmatched faces use a system fallback and are listed in `meta.json` `fontFallbacks`.
- **Re-import**: refreshes markup, styles, assets, meta and variables only. It never modifies `motion.ts` or anything in `versions/`, so motion work survives a re-import. Version files stay `v1.ts`, `v2.ts`, … without gaps.
- **Motion**: v1 is a scaffolded default entrance (`lineage: 'imported from <figma link>'`). Imports never invent motion beyond that.
- **Scaled frames**: if the linked frame is a scaled instance, `designWidth` records the native width. The lab lays the component out at `designWidth` and zooms to `frame.width`.
- **Issues**: record Figma file problems for designers (no auto layout, unnamed layers, variant strings as layer names, values not bound to variables) in `meta.json` `issues`.

### Page import (a Figma page frame becomes components plus a page)

For ideation, a designer links a whole page frame. Components stay the unit of motion (and of approval); the page is the list of them in order, and page versions (see Architecture) combine their versions. Do the file-writing with `npm run figma:import-page -- <manifest.json>` (`scripts/figma-import/page.ts`; the manifest shape is in `page-cli.ts`).

1. **Read the frame.** `get_metadata` on the page frame: it is usually a wrapper (a breakpoint or state, e.g. `xl · open`) holding a column of section instances plus chrome. Look at the screenshot; get the design context of each section.
2. **Sections vs chrome.** Sections sit in the page flow and are imported. Chrome (an off-canvas menu, the global header, the footer, floating buttons) is listed in `notImported` with the reason, not imported on a first pass: they are usually interactions of their own, imported when the designer asks. Ask when unsure.
3. **One component per distinct section, identified by what it is, not its layer name.** Figma instance names are shared by variants (three `section header` instances of different heights may be one component with different content, or different variants). Compare structure: the same structure repeated is one lab component in several slots (`section-header-1`, `-2`); a different structure (with a photo, without one) is a separate lab component named for what differs (`section-header-image`), never numbered. A section that is an instance of something already imported (match `meta.json` `layerName`, the Figma component and the size) reuses that component instead of importing again. Content inside a section (the quote cards in a quote slider) belongs to that component; there are no nested components on a page.
4. **Import each new component first** with the component import rules above (fix-up passes, baseline). Each is laid out at the content column width (the page's `width`, e.g. the 1136px column inside a 1440px frame).
5. **Write the manifest and run the page import.** It writes `pages/<id>/page.json` (slots in order, `width`), `pages/<id>/meta.json` (Figma link, frame, sections with their Figma names, what was not imported, issues) and, first import only, page version `v1` (every component's default version). It refuses a section whose component is not imported yet, and names them.
6. **Check it in the Page view** against the Figma screenshot: order, and that sections sit flush the way the frame does.
7. **Re-import** rewrites `page.json` and `meta.json` and never touches saved page versions; it reports any saved version that no longer fits (a slot that went away). Fix those by editing the version, not by deleting it silently.
8. Record page-level Figma problems in `meta.json` `issues` (sections not named, variants told apart only by layer name, chrome inside the page frame).

### Fidelity target

The component's static end state (after all animations finish) must match the Figma screenshot within **5%** of pixels (`MAX_DIFF_RATIO` in `tests/e2e/visual.ts`, pixelmatch threshold 0.1). Fix the markup/styles to close a gap rather than raising the threshold.

### Visual check

- `/?view=frame&component=<name>&version=<id>` renders the component alone at its Figma frame size, with no lab chrome.
- `compareToBaseline(page, component, version)` in `tests/e2e/visual.ts` loads that view at the baseline's size, waits for fonts, images and animations, and diffs against `tests/baselines/<component>.png` (the Figma screenshot). Actual and diff images are written to `tests/visual-output/` (gitignored).
- Each imported component adds an E2E spec that renders it, plays each version without console errors, and calls `compareToBaseline`. Commit its baseline PNG.
- Unit tests for the importer use a generic fixture built in a temp directory (`tests/unit/figma-import.test.ts`); do not commit a real client component as a fixture.

## Designer workflow

Designers do not know git and work only through Claude. Handle version control for them, silently. **Never use git jargon** (branch, commit, merge, rebase, conflict, PR, push, pull, stash, diff) in replies unless the designer uses the word first; then mirror their vocabulary. Don't mention git at all unless asked.

### First run on a new machine

On a computer you have not set up yet in this conversation, or whenever the lab will not start, **before Session start** check that the machine is ready. Designers should not have to know what Node, npm or Playwright are.

1. Run `npm run doctor -- --json` (plain Node, so it works even on an old one; if `npm` itself is missing, tell them Node is not installed). Read `ready` and each result's `status` (`ok`, `warn`, `fail`, `info`), `title` and `fix`.
2. Say what is wrong in plain words and why it matters ("The lab needs a newer version of Node, the engine that runs it"), never the error text. Ask before you install anything, and do one thing at a time, in this order:
   - **Node** (`fail`): with nvm, `nvm install` in the project folder (its `.nvmrc` says which); with no nvm, install nvm first (`https://github.com/nvm-sh/nvm`, with their OK) and open a new shell. Never use `sudo`.
   - **Packages** (`fail`): `npm install`. It also sets the merge protection for the token files.
   - **Git** (`fail`, a Mac): `git --version` makes macOS offer the Apple command line tools; they accept and wait.
   - **Test browsers** (`warn`, a `fail` for `npm run check`): `npx playwright install chromium webkit`, a download of a few hundred MB once per computer. They are needed before "Ready for review", so do it early, not at the end.
3. What you cannot fix yourself, say who can: the **client fonts** (`warn`; the lab works with a fallback typeface, but it will not look like the client's, so ask whoever holds the files and put them in `/fonts`), the **Figma connector** (`info`; check that it is connected in Claude Code and signed in with access to the client's file, and if not, send them to connect it), **GitHub access** to the project repo, and the **project name** (`project.json`).
4. Run the doctor again until `ready` is true. Warnings do not block the work. Then Session start.
5. If `npm install` stops with "Unsupported engine" or `npm run dev` prints "The lab can't start yet", that is this: fix the cause (Node), never edit `.npmrc` or `engines` to get past it.

### Session start

1. Learn the designer's first name (ask once if unknown) and what they want to explore.
2. Pull the latest `main`, then create a branch named `<designer>/<exploration>` (kebab-case, e.g. `maya/hero-entrance`) from what they describe. If they are continuing earlier work, switch to their existing branch and bring it up to date with `main` instead.
3. Start the dev server and open the lab in the browser (`npm run dev`), on the component or page they're working on.
4. **Before they start on a component or page, say who else is on it.** Run `git fetch`, then for each other designer's pushed branch (`git branch -r`) check `git diff --name-only main...origin/<branch>`; if one touches the same component or page folder, tell them in design terms ("Claudia has a hero exploration in review that changes the same card") and let them choose. Work that is only saved on someone's Mac can't be seen. One designer owns the import of a given Figma frame: a re-import rewrites that component's markup and styles, so don't re-import a frame a teammate imported without asking them.
5. Greet them with what's ready ("The lab is open on the hero. What should we try?"), not with setup details.

### "Save this"

Commit everything they've changed with a clear, descriptive message (what changed and why, e.g. "Hero v3: slower fade with a slight rise"). Confirm in plain words naming what was saved ("Saved hero v3"). Do not show hashes or file lists.

### "Ready for review"

1. Set `status: 'review'` on the **component** (`components/<name>/motion.ts`, on the `ComponentModule`) they're submitting; the versions they're sending must already have `forkedFrom` or `lineage` set. Only mark the component `approved` or `archived` when the designer asks.
2. Run `npm run check`; fix anything that fails before continuing. If you can't fix it, explain simply what's wrong.
3. Save, push the branch, and open a pull request titled after the exploration, with a short plain-language summary of what changed.
4. Give them the link: "Sent for review: <link>".

### When others changed the same work

Before saving and before sending for review, bring in the latest `main`. If someone else changed the same files:

- **Resolve automatically when safe**: edits to different parts of a file, identical changes, or independent additions. Keep both sides. Explain in one simple sentence ("Someone updated the card styles; I kept their change alongside yours").
- **Version numbers**: if both sides added the same version id (e.g. both made `v3`), renumber the designer's to the next free integer (file, `id`, export, `versions` array, tests). Never skip or reuse numbers.
- **Token files are the project's own** (`tokens/motion.json`, `presets.json`, `figma-variables.json`, `visual.css`, `fonts.css`): `.gitattributes` gives them the `project-owned` merge driver (keep ours) and `npm install` sets it (`scripts/setup-git.mjs`). **Before any merge from the template in a project repo, check `git config merge.project-owned.driver` says `true`; if not, run `npm install`.** A template merge then never touches them. To take a template token change on purpose, see "The token files are the project's own" in README.md (`git checkout template/main -- tokens/motion.json …`, then `npm run tokens:remap -- --renames …`).
- **A token file must never silently lose a teammate's change.** The `project-owned` driver keeps *our* version when the same part of one of those five files changed on both sides, which is right for the template but drops a teammate's change when two designers edited the same token file (two Figma imports both write `tokens/figma-variables.json`). After any merge of `main`, compare each of the five files with `main`'s (`git diff origin/main -- tokens/`): if our file lost something `main` had, say so in design terms ("Miguel added three variables from his import that mine would have dropped"), and keep both by hand (merge the entries) or ask which to keep.
- **Ask only for a real design choice**: both people changed the same motion value or the same version's look. Describe the two options in design terms ("Their hero fades in over 400ms, yours over 600ms. Which should we keep?"), then apply the answer.
- After resolving, rerun `npm run check`.

### Designing states and triggers with a designer

A designer says "the hover state should lift it, a click opens that" and Claude writes the version. Say it back in design terms, never in code terms ("hover lifts the card 4px and the image scales to 103%").

1. **Fork first.** A new interaction is a new version (`forkVersion`), never an edit of someone else's. A component that should appear and then respond ("fade in like v1, then lift on hover") forks the entrance version and adds `interaction` to it: one version with both, the entrance first and the states live after it. Ask whether it appears first when the designer hasn't said.
2. **Ask only what the designer hasn't said, and never invent it:** which element reacts (the whole component, or a named layer such as the image or the close button); what each state looks like (how far, how much, fade or not); **name the states in the kit's words: `default` (where it starts), `hovered`, `pressed`, `focused`** (a click-driven state is named for what it is: `open`, `closed`), never `rest` or `hover`; how long and how it feels (name a duration and an easing token; productive for small UI responses, expressive for large ones; exits are shorter than entrances and use productive easings); whether press and focus should look different from hover; what leaving does (back to rest, usually quicker); and, for click, whether it sets a state or toggles two. Hover on touch screens does not exist, so ask what a touch user should see if hover carries information.
3. **Write it in the version file, never in the markup.** Triggers are `interaction.triggers`; the only markup a version needs is `data-motion="<layer>"` on an inner element, and a re-import of the Figma frame **replaces the markup**, so a layer's `data-motion` name must be checked after a re-import (the lab skips a layer with no element, and "What it does" still lists it).
4. **Use tokens.** States name tokens (`translateY(-{distance.4})`, `scale({scale.95})`); a value no token has is a proposal for a new token (new tokens start experimental), not a literal.
5. **Anything outside the component is the developer's:** a button elsewhere that opens a panel has no trigger here; say so ("the open state is set from outside") and leave a state with no trigger. The spec says the same.
6. **Check it in the lab and read it back.** Open the version, hover, press and tab to it for real, try Interrupt, and say back what it does in plain words (the "What it does" list is switched off in the Details panel, but `summarizeInteraction` still writes it): if it doesn't match what they meant, the version is wrong. Try both runtimes (CSS and Motion); under Motion the timing is duration and bounce.
7. **Tell them what a developer gets:** CSS hover, press and focus work with the stylesheet alone, and the GSAP and Motion files have an `attach…` function. Set `trigger`/`reducedMotion` only when the designer has said (an interaction version's own triggers are not the entrance `trigger`).
8. **Not supported yet:** drag, physics springs and carrying speed through an interruption, Compare for interactions, and reading Figma variants as states. Say so plainly rather than approximating them.

### Entrances with presets

When a designer wants a standard entrance ("the eyebrow, title and text rise in like our usual"), use the **entrance presets** (eyebrow, title, text, card, media, ui; see "Entrance presets"): write element + preset + delay (and a stagger for repeating elements) instead of raw durations and easings. Show them the Presets view. Only write a custom motion (model and keyframes) when they want something a preset isn't; don't change a preset's values for one component (a preset is a system decision).

### Rules of thumb

- Never work directly on `main`; never discard a designer's changes without asking.
- Don't edit another designer's version files; add a new version instead.
- A **global scale** renames tokens across the project: apply one only when asked, preview it first, make sure their work is saved, and say what it changed in design terms (see "Using the scale").
- If something goes wrong with saving or syncing, say what it means for their work ("Your changes are safe, but I couldn't send them yet") and fix it, rather than reporting git errors.

## Scripts

| Command              | Action                                          |
|----------------------|-------------------------------------------------|
| `npm run figma:import -- <manifest.json>` | Import a Figma frame as a component |
| `npm run figma:import-page -- <manifest.json>` | Write a page (and its first page version) from a Figma page frame whose sections are already imported |
| `npm run spec -- <component> [version] [--format gsap\|motion\|all]` | Export motion.css, tokens.css and spec.md (plus GSAP or Motion code) for a developer; the project's shared presets go once to `export/presets/` (`npm run spec -- --presets` writes just those) |
| `npm run tokens:scale -- <kind> <scale>` or `-- --all <scale>` | Regenerate distance, duration, delay, opacity and/or scale from a scale (`--dry-run` to preview) |
| `npm run dev`        | Start Vite dev server (http://localhost:5173, also http://motionlab.localhost:5173: any `*.localhost` name reaches your own computer with no setup, which `.dev` or `.lab` would not; the desktop preview opens the `.localhost` one) |
| `npm run build`      | Build to `dist/` with relative paths            |
| `npm run typecheck`  | TypeScript type check (no emit)                 |
| `npm run test`       | Run Vitest unit tests                           |
| `npm run test:e2e`   | Run Playwright E2E tests (starts dev server; `PORT=5200 npm run test:e2e` when another server holds 5173) |
| `npm run test:e2e:fast` | Playwright in Chromium only (about half the time) |
| `npm run check:changed` | typecheck + every unit test + the browser tests only for the components and pages you changed (a few seconds to 15s): **what to run while working**; a change to the lab, tokens or scripts runs `check:fast` instead; `-- <component>` names one |
| `npm run check:fast` | typecheck + test + Chromium e2e (about a minute in the template, about 25s in a project): when the lab or tokens changed |
| `npm run check`      | typecheck + test + build + test:e2e: **before review**. Chromium runs everything (a project: its own components and pages), WebKit runs the motion tests (every version, triggers, reduced motion, each component's spec) |
| `npm run check:all`  | `check` with the lab's own specs and WebKit's screens included, in a project too: after a merge from the template, and before a release |

**`npm run check` must pass before sending work for review** (and `npm run check:all` after merging from the template). While working and before a save, run `npm run check:changed`: typecheck, all the unit tests and only the browser tests for what you touched. Other ways to run less: `npm run check:fast`, one spec (`npx playwright test tests/e2e/<file>.spec.ts --project=chromium`) or one unit file (`npx vitest run tests/unit/<file>`). **Where the time goes** (measured): the unit tests, typecheck and build are about 10s; the browser tests are the rest, so a project skips the lab's own specs (`LAB_E2E_FILES` in `tests/samples.ts`: the template tests the lab, a project only merges it, `LAB_TESTS=1` runs them), WebKit skips the lab's screens (`WEBKIT_SKIP_FILES`, `WEBKIT_ALL=1` runs them), and `tests/e2e/all-versions.spec.ts` loads the lab once per component and opens each version from its tab (it used to load the lab per version, and grew with every one added). The e2e tests run fully in parallel (`fullyParallel` in `playwright.config.ts`); keep each test independent (own page, no shared state) and avoid fixed sleeps so they stay safe that way.
